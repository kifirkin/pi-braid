# src/extensions/core/ - Input/Output Shaping

Extensions that shape what the LLM sees at runtime: platform shims,
environmental awareness, and system prompt assembly.

## Sub-extensions

| Path                 | Purpose                                                                                                                                                                                                       | Depended on by   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `polyfill/`          | Polyfills for missing pi core features.                                                                                                                                                                       | (foundation)     |
| `agent-environment/` | L1 environmental awareness: working dir, time, machine info.                                                                                                                                                  | `prompt-builder` |
| `bash-cwd/`          | pi's `bash` tool, overridden so the shell's working directory carries across calls. See `bash-cwd/AGENTS.md`.                                                                                                 | (tool surface)   |
| `prompt-builder/`    | Builds the agent's system prompt. Composes sections; orchestrates once-per-session whisper deliveries from `memory/` and `cognitive/`.                                                                        | (final assembly) |
| `skills-tool/`       | Skill surface: `list_skills` catalog (on-demand reach and ranking) + `skill_stats` counters, the auto-inject whisper, the skills floor (visible catalog) and drift trigger text rendered by `prompt-builder`. | (tool surface)   |

## Local Contracts

- These are the **always-loaded** infrastructure. Other extensions can assume they are present.
- If you need a new infrastructure piece, add it here.
- Agent-facing working tools (scratchpad, workspace snapshot) live in `memory/`.
- Cognitive analysis tools (think/verify/etc, detectors) live in `cognitive/`.
- Self-management extensions live in `self/`.
- Time-based events live in `scheduling/`.
- Whisper deliveries (hints, past insights, OpenSpec) live in their natural homes (`cognitive/`, `memory/`). The prompt-builder orchestrates the once-per-session call to each `deliver*` function but does not own the data pipeline.

## Skills adoption contract

Two surfaces in `skills-tool/` put a skill body in front of the agent: the auto-inject whisper, before the prompt is answered, and the at-use line, after a call in a family a file's `governs:` declaration names has already run. The rules about whether either arrived live in one place, here, and nowhere else:

- **Delivery is observable.** `sendTrackedMessage` returns a boolean: `true` when the message was handed to `pi.sendMessage` (immediately or on the deferred triggerTurn macrotask), `false` when a suppression path dropped it (cognitive nudges disabled, per-turn/per-source flood cap, reprime cooldown). A suggestion is delivered with the park class (`delivery: "park", deliverAs: "steer"`) at source `skills-auto-inject`, which pi-core appends to the session stream - immediately when the session is idle, at the turn's end when a run is active. Both land in the session JSONL; a suppression upstream of `pi.sendMessage` reaches no stream at all.
- **Counters move after delivery.** `recordSkillSuggestion` runs only on a `true` return, and the cooldown/LRU bookkeeping runs after the send too, so `suggested` counts arrivals and an undelivered suggestion consumes no slot. The suggestion bypasses the per-turn whisper cap (`bypassFloodCap: true`) because prompt-builder's once-per-session hygiene whisper fires earlier in the same `before_agent_start` at the same priority and would otherwise spend the only advisory slot; the module's own budget (cooldown turns, max active suggestions, one send per turn) is the bound that keeps the whisper a whisper.
- **The relevance decision is the utility model's.** `skills-tool/ranker.ts` ranks the visible catalog against the prompt as `name - first sentence` rows and reads back at most three `{name, why}` entries. One call per turn at most, none for a prompt shorter than `RANKER_MIN_PROMPT_CHARS`, and the session's own answer for a repeated prompt (the cache is keyed by prompt hash), because the call sits in front of the turn it informs. The parse is strict: an unknown name, a malformed array or a refusal yields no rows and a recorded reason, never a repaired guess. Nothing in this path consults an authored trigger phrase and no phrase match is kept as a fallback: with no utility model, no key, an error or a timeout the whisper is silent, the reason lands in the log, and `skill_stats` reports the rate as `ranker.ranked` / `ranker.rankedCached` / `ranker.rankedFailed`. The ranker's order is kept as answered; the session's cooldown and slot budget are the only thing delivery adds. The first row's message carries that skill's whole SKILL.md body (frontmatter stripped), capped at `FULL_BODY_MAX_CHARS`, and its opening line prints the model's clause for it; a body past the cap is cut once at a word boundary, and the message names the file and says the rest is there, so a cut is never silent. Every lower rank stays on the pointer tier (`MAX_EXCERPT_CHARS` of body plus the read path). A body is delivered at most once per skill per session: the session's `fullBodies` set is written with the delivery, and a skill that answers again is a pointer. `fullBody` moves only for the message that carried a body while `suggested` moves for every delivered suggestion, so the share of bodies among deliveries is computable from `skills-usage.json` alone.
- **Conversion is a detected read.** The whisper asks the agent to open the SKILL.md; the conversion signal is the `read` tool_result (`actual`), which is also what sets `hadSkillLoad` in the durable session record. A skill whose body the whisper already carried needs no read, and that delivery is counted as `fullBody`; the read stays the signal for the rows the message signposted instead. The retired LOADED/SKIP reply is no longer solicited; `claimed` keeps its historical honor-system meaning and stays monotone.
- **A compaction returns the body, it does not ask for a re-read.** Each landed body is checked by its own 120-character head (`bodySignature`) against the model-visible projection. A body still there needs nothing; a body gone comes back as its own bytes, capped at `FULL_BODY_MAX_CHARS`, under one header line naming the skill and the file it came from, and the session's `returned` counter moves on the accepted send. A body past that cap, or a file that vanished between the read and the check, gets the one-line pointer instead and moves `reloads`: a truncated skill file is a paraphrase with extra steps, so the fallback names the file rather than cutting it. One delivery per skill per session (`state.reload.announced`), so a second compaction that finds the same body absent describes the same loss once. The `reloads` series is durable and `returned` is session-scoped by design: the rescue is a property of one session's compaction, not of the skill's adoption. Instruction files a session read ride the same cycle through `memory/context-manager`'s curator. Fixtures: `test/runtime/core/test-skill-reload-after-compaction.mjs`, `test/runtime/lib/test-compaction-reinject.mjs`.
- **The trigger has a mechanical form.** `skills-tool/loading-guidance.ts` carries both the judgment form (the task entered a listed skill's domain) and the mechanical form (about to call a tool family whose word appears in a skill's name). `prompt-builder` renders that text through the `skillsLoadingText` builder as the `skills-loading` section and holds no copy of the rules; the trigger's worked examples are derived at assembly from the live tool and skill names, so the text names no pair that the running session does not have. The identity's skills prose stays one sentence.
- **The catalog is in the prompt.** The same section renders every visible skill as one `- name: description` row, with the read path derived from the skills' own file paths (one root for a single pack, a directory heading per pack when a catalog is installed from several). A tool call is no longer the way the agent learns which skills exist: the floor exists because the prompt that opens a resumed session carries no domain vocabulary for a matcher to rank against. `list_skills` remains the price tool (reach, headings) rather than the catalog: a call that names no page and no page size returns the whole catalog in the order this section renders (`catalogOrder`: each pack directory, its rows by name), identical call to call, and `rank: "relevance"` is the explicit request for the ranked view with its verdict.
- **A retired skill is not advertised.** A SKILL.md whose frontmatter declares `status: merged`, `archived` or `deprecated` stops being advertised and matched, and the file stays on disk as history. The exclusion rides the flag `disable-model-invocation` already owns (derived at cache time in `index.ts`), so the catalog, the suggestion whisper, the at-use line, the accessor and `list_skills` agree without a second concept. The row stays in the unfiltered cache, so a read of the file still resolves.
- **Drift re-points at the floor.** When the session's own path-taking calls (`read`/`edit`/`write`) accumulate entries in a work area the floor was not rendered against, one steer line names that area and points back at the catalog. The rule and its bounds (two entries, one fire per twelve calls, three per session, quiet for the same window after any skill surface) live in `loading-guidance.ts` beside the floor text; the wiring is the `tool_result` handler in `auto-inject.ts`. Bounds are the whole design: the line is only worth its noise if it stays rare.
- **The at-use line is observed, never enforced.** With `braid.skills.inform` set to `inform` (default `off`), a `tool_result` whose call **succeeded**, whose tool name yields a family token some visible cached skill declares with `governs:`, and whose obligation row carries no `read` leg emits one steer line naming the file path and the family. It runs after the result exists, returns no replacement, and refuses, delays and rewrites nothing: any gating change can only make it quieter, which is the property that separates it from a refusal gate. The payload is derived from the declaration and the catalogue entry only (the skill's own `filePath`, the token the call's name yields), so no skill name is invented in code and no tool argument is echoed. Once per session per skill, suppressed by the same obligation record the legs write (its `informed` leg), silenced by a read or by a first-class body delivery at any point, and hidden skills are never named. `skill_stats` reports it as `inform` from the store: `undecided` below twenty informs, `beats` only when the lower Wilson bound clears the suggestion channel's 18.8% pair conversion, `noise` otherwise.
- **Applicability is not judged from phrases.** The pass that classified a task against the trigger phrases a file declares is gone with the matcher that fed it: a phrase table cannot decide applicability for a task written in a script it does not carry, and keeping it beside the ranker would leave two answers to one question. What a session applied is now the ranker's answer for that turn, visible as the suggestion itself; `skill_stats` still reads `kind: "applicability"` rows, so a store written before the pass was removed is reported unchanged, while a new session writes none and the `applicability` / `obligations` blocks stay absent from its reply. The obligation legs (`suggested` / `listed` / `informed` / `read` / `applied`) are unaffected: they are written by the surfaces that observe them, not by the applicability pass.
